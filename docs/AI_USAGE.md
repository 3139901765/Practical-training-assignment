# AI_USAGE.md — 本作业的 AI 使用透明说明

## 1. 用了哪些 AI 工具

- 开发全程由 AI 编程助手（Codex，GPT-5 系列模型）在本仓库内完成：数据分析、代码编写、测试与文档。
- 产品内的「数据问答」功能支持 DeepSeek（OpenAI 兼容接口，配置 `DEEPSEEK_API_KEY` 后启用）或内置 mock 意图解析；两者走同一条真实工具调用链路。
- 未使用其他生成式工具生成业务数字。

## 2. 怎么拆任务（真实 prompt 示例）

把作业拆成 8 个可验收的里程碑，每个里程碑完成即提交一次 git：

1. 脚手架 → 2. 数据清洗 → 3. 建库 → 4. API+测试 → 5. AI 链路 → 6. 前端 → 7. 真值测试 → 8. 文档

给 AI 的真实 prompt（节选，即本作业开发开始时收到的实现指令）：

> 文件中 data 文件夹里有三张表……README.md 中有三个任务以及要求，请你分析完毕后，为我完成这三个任务。

以及实现阶段的关键约束 prompt（来自 README 原文）：

> 回答里的数字必须来自你的 API / 数据库的真实查询结果，不能让大模型凭 CSV 原文瞎编。
> 处理"AI 答不了的问题"，要有合理的兜底而不是编造。

AI 据此先做数据体检（发现重复 80 组、缺失金额 160 行、脏外键 50 行、日期格式 3 种等），再定口径，最后实现。

## 3. AI 在哪里出过错 / 差点编数字，怎么发现、怎么修的

| 问题 | 怎么发现 | 怎么修 |
|---|---|---|
| 模拟清洗时把「负金额 + 无效数量行」误读为金额与单价不一致（74 条），若直接写进报告会误导评审 | 用独立脚本逐行对账，发现 74 = 49 + 25，全部是待剔除行 | 清洗后再校验，报告写明「清洗后金额 = 单价 × 数量，0 条不一致」 |
| mock 意图解析把「奶茶 六月卖了多少钱」误判成综合看板（overview） | 真值测试用例「查无此商品」失败 | 新增 `notFound` 意图：问「XX 卖了多少钱」但查无 XX 时明确回答「数据中没有」，而不是答成看板 |
| 「poke 六月卖了多少钱」命中 3 款商品 | 测试「模糊商品名」失败 | 返回多候选并引导用户说具体商品名，不替用户猜 |
| 「客单价最近是涨了还是跌了」环比窗口落在数据范围外（对比区间无数据，显示 ¥0.00） | 手工验证示例问题 | 整月区间自动对比上一自然月：7月 36.05 vs 6月 35.18，涨了 +2.47% |
| 数字校验器对负百分比误报（模板写「下降 2.89%」，校验器找「-2.89」） | 服务日志出现 verifier 报错 | 校验器接受绝对值（方向由「上涨/下降」文字表达） |
| 前端聊天返回空响应 | 联调时 API 返回空 JSON | 发现 Express 4 未 await 异步路由，改为 Promise 链式处理 |
| DeepSeek 若拿到自由发挥空间可能改写数字 | 设计阶段主动预防 | 数字只走确定性模板，模型只输出工具调用；模型未调用工具时一律按 FALLBACK 处理，不放行自由文本 |

核心结论：**「AI 会编数字」是工程问题，不是靠提示词能根治的**。本作业的解法是让模型不接触数字——模型只负责意图理解，数字由 SQL 产出、模板渲染、校验器兜底，测试逐位断言。

## 4. 哪些部分决定自己写，为什么

- **清洗规则与 SQL 查询**：数字正确性的地基，必须确定性、可审计，逐行手写。
- **答案模板与数字校验器**：防止模型改写数字的关键防线，写死比提示词可靠。
- **测试**：23 个用例覆盖「AI 回答 = 数据库查询」，这是评审要的证明，不能由 AI 生成后不验证。
- **UI 设计**：作业明确「不是套个组件库就行」，视觉与交互自己设计。

用 AI 的地方是它擅长且可验证的：意图解析规则、代码结构搭建、文档初稿——但所有数字结论都经过脚本对账与测试复核。
